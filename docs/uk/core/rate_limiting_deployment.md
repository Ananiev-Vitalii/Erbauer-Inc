# Розгортання спільного rate limiting

Це вимоги розгортання. Успішні локальні автоматизовані тести не підтверджують
безпеку ingress розгорнутого застосунку на Render.

## Джерело IP

- Local: `CLIENT_IP_SOURCE=remote_addr` (також значення за замовчуванням).
- Render Free і Paid, public ingress: `CLIENT_IP_SOURCE=render_cloudflare`.
- X-Forwarded-For не використовується. Відсутня або некоректна адреса дає
  `None`, а ключ rate limiting — `no-ip`.

Одна реалізація використовується для обох тарифів. Режим не визначається
автоматично за тарифом, доменом або DEBUG. `config/settings/base.py` читає
`CLIENT_IP_SOURCE` через `os.getenv` після завантаження dotenv. Наявні environment
variables мають пріоритет: `load_dotenv` викликається без `override=True`.
Непідтримуване значення спричиняє ImproperlyConfigured під час визначення IP.

У `.env.example` наведено локальне значення `remote_addr`. Для локального
запуску використовуйте `config.settings.dev` і налаштоване Redis-підключення:
сам `config.settings.base` не налаштовує Redis cache. Файли з реальними
секретами maintainer налаштовує самостійно.

Для Render Free задайте `CLIENT_IP_SOURCE=render_cloudflare` в Environment
сервісу. Для Paid із власним доменом задайте те саме значення. Для обох
використовуйте `config.settings.prod` і наявний `REDIS_URL`; окремий Redis URL
для limiter не потрібний. Після зміни налаштувань перевірте deployment.

Довіра до CF-Connecting-IP дозволена лише за гарантованого проходження
недовірених запитів через public ingress Render/Cloudflare, який перезаписує
цей заголовок. Сам заголовок не доводить походження запиту.

На Paid перевірте private-network доступ. Відсутність запланованих приватних
викликів не блокує їх технічно. Недовірені сервіси не повинні мати приватного
HTTP-доступу до Django. Ізоляція між environments не ізолює сервіси всередині
одного environment. Якщо цю межу неможливо забезпечити, не вважайте режим
render_cloudflare захищеним від приватного spoofing: спочатку потрібне рішення
щодо мережевої ізоляції або підтвердженого розрізнення ingress.

Власний домен і onrender.com потрібно перевірити окремо, підставляючи XFF та
CF-Connecting-IP у контрольованих запитах. Локальні заголовки завжди ігноруються.
Не вмикайте довіру лише тому, що запит містить CF-Connecting-IP. Перехід із Free
на Paid потребує повторної перевірки приватної доступності, навіть якщо код
і значення CLIENT_IP_SOURCE залишаються незмінними.

## Redis

Limiter використовує RedisCache з CACHES.default та його наявний pool.
Окремий URL або pool не створюється. LocMem не є fallback для limiter: без
Redis захищені запити повертають 503. Інші механізми cache не змінюються.

Upstash підтримує EVAL/EVALSHA. Перевірте права конкретного користувача, Lua
ліміти, квоти, eviction та socket/connect timeouts поточного cache-підключення.
Limiter не змінює параметри спільного pool. Неоднозначні timeout виконання
не повторюються; NOSCRIPT дозволяє EVAL, бо скрипт ще не виконувався.

Очікувана відмова limiter обробляється спільним CBV mixin. Contact повертає
HTML partial із заповненою формою та HTTP 503; authentication views — автономну
сторінку 503. Рендерення цих відповідей не передає request у render_to_string,
щоб не викликати cache-залежні context processors. Сторінка 503 використовує
локальні Bootstrap та errors.css, не успадковує base.html і не читає профіль
компанії. Захищена операція не продовжується. Помилки скрипту/формату даних,
які реалізація розпізнає як дефекти, не підміняються повідомленням про мережу.

Ключі rate_limit:v2 містять числові значення, не pickle-словники. Prefix і
version застосовує Django. Після переходу обмеження старого namespace не
переносяться, а старі ключі завершуються за TTL. Не очищайте Redis.

У цих операціях беруть участь лише поля з непорожніми нормалізованими значеннями.
Window зберігає семантику паузи: реєстрація спроби нижче порога, коли жодне
з переданих полів не заблоковане, збільшує лічильник кожного переданого поля
та поновлює його window TTL. Це не точний sliding window.
Читання стану не змінює лічильники або TTL.

Коли будь-яке поле досягає порога, ця реєстрація повертає стан блокування,
встановлює ключі блокування для всіх переданих полів на налаштований cooldown
і видаляє їхні лічильники спроб. Поки будь-яке передане поле заблоковане,
реєстрація повертає наявне блокування без збільшення лічильників і без поновлення
window TTL або cooldown. Отже, заблоковані запити не продовжують cooldown.
Reset видаляє ключі спроб і блокування лише для переданих scope та полів.

Реєстрація всіх полів і блокування атомарні в межах одного виклику Lua;
весь HTTP workflow не стає транзакцією Redis. Пороги, scopes і налаштовані
тривалості window/cooldown не змінюються.

## Стан перевірок і перевірка deployment

Maintainer підтвердив успішний запуск 81 звичайного backend-тесту та
8 opt-in Redis integration tests в ізольованому локальному середовищі.
Звичайні тести покривають contact workflows і спільний rate limiting, зокрема
NOSCRIPT, відмови сховища та захист від повторного виконання після неоднозначних
timeout. Redis integration tests перевіряють реальний Lua: блокування всіх полів
за порогом, поновлення та завершення window TTL, читання без поновлення TTL,
завершення cooldown, заблоковані запити без продовження cooldown,
reset у межах scope та конкурентні запити.

Ці результати не замінюють deployment-перевірок public ingress Render,
власного домену, onrender.com, приватної мережевої доступності та поточних
прав, лімітів і timeout Upstash. Повні регресії authentication/Turnstile workflows
потребують окремої перевірки; запуск тестів main/core не підтверджує покриття
всіх workflows додатка user.

Тести не повинні використовувати development або production cache, broker чи
Redis. Для opt-in Redis integration tests використовується лише ізольований
локальний Redis у Docker; зовнішні email providers і реальні Celery workers
не використовуються. Нові переклади, як і раніше, потрібно витягти й скомпілювати
в development environment після додавання. Під час цього оновлення документації
тести, deployment-перевірки та команди перекладу повторно не запускалися.
