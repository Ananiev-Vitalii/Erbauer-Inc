# Views додатка Main

Документ описує views, зареєстровані в `main/urls.py`. Чотири власні класи
розташовані в `main/views.py`; Privacy Policy використовує Django `TemplateView`
безпосередньо в URL-конфігурації. Усі views публічні й не вимагають входу.

## Спільний контекст запиту

Описані нижче сторінки читання обробляють GET і стандартні HEAD/OPTIONS;
непідтримувані методи повертають 405. Звичайний рендеринг запускає глобальні
context processors. Зокрема, `main.context_processors.company_base` завантажує
мовний кеш даних компанії, а для авторизованого користувача виконує запит до
`account.Profile` через `employee__user`. Для анонімного користувача запиту
профілю немає. Контактні partial явно обходять ці processors.

Активна мова Django визначає переклади та ключі кешу даних. Поточний
`config/urls.py` не додає мовного префікса до маршрутів. Кеш-сервіси використовують
`CACHE_DEFAULT_TIMEOUT` (типово 900 секунд); за звичайного cache miss дані
завантажуються через ORM. Сигнали save/delete для CompanyProfile, Service,
Project, TeamMember, Employee та Position планують інвалідацію після commit
транзакції. Це не охоплює `QuerySet.update()` і bulk-записи, які обходять save signals.

## HomePageView

**Призначення / запит:** Головна сторінка GET `/` (`main:home`).

1. Завантажити послуги, видимих учасників команди, активний профіль компанії та
   останні чотири проєкти через мовні сервіси кешування даних.
2. За cache miss вибрати найновіший активний профіль компанії, упорядкувати
   послуги за назвою, проєкти — за спаданням ID. Видимих учасників завантажити
   за порядком відображення разом із працівником і посадою через `select_related()`.
3. Розділити послуги на групи по шість (`service_pages`). Установити
   `has_more_team_members`, якщо завантажено понад чотирьох учасників;
   view усе одно передає повний список видимих учасників.
4. Додати незв'язану з даними `ContactForm` і відрендерити `main/home.html`
   із підготовленим та описаним вище спільним контекстом.

**Результати:** Зазвичай 200. Відсутній профіль дає `None`, порожні колекції
залишаються порожніми. Контактна спроба чи email-задача не створюється.
HTML fragment cache немає: view звертається до кеш-сервісів даних на кожний
запит. Окремого обробника 503 для помилок кешу/ORM тут немає.

## ContactFormView

**Призначення / запит:** Обробити POST `/contact/submit/`
(`main:contact_submit`) і повернути HTML partial контактної форми. GET та інші
методи, включно з HEAD/OPTIONS, повертають 405. Стандартний CSRF middleware
залишається активним; відхилена CSRF-перевірка повертає 403 до обробки форми.

1. Прочитати IP-based стан limiter у scope `main_contact_form`. Вибір IP
   визначає `CLIENT_IP_SOURCE`; відсутній або некоректний вибраний IP дає `no-ip`.
2. За наявного блокування повернути bound-форму з переданими даними та
   локалізованим повідомленням cooldown. Інакше атомарно зареєструвати спробу
   в Redis. Якщо вона досягла порога, повернути таку саму bound-відповідь.
3. Лише за дозволеної спроби перевірити `ContactForm`: обов'язкові ім'я, телефон,
   повідомлення та згоду з Privacy Policy, обмеження довжини й дозволені формати
   телефону. Форма нормалізує валідний телефон до `+1XXXXXXXXXX`. Невалідна форма
   повертається bound із помилками. Невалідні надсилання також враховуються.
4. Для валідної форми опублікувати `send_contact_email_task` лише з очищеними
   `name`, `phone`, `message` та активною мовою. Представлення аргументів задачі
   приховане, retry публікації вимкнено. Об'єкт request не передається.
5. Якщо публікація спричинила Kombu `OperationalError`, повернути bound-форму
   з локалізованою технічною помилкою. Після успішної публікації повернути нову
   форму з `is_success=True`. Це підтверджує подання, а не доставку email.
6. Відрендерити `main/includes/sections/contacts.html#contact-form` із маркером
   `data-contact-form-response`. Додати CSRF-токен через `get_token()` і викликати
   `render_to_string()` без request: глобальні context processors не запускаються.
   Повернути HTML із переданими status/параметрами відповіді (типово 200),
   зберігши токен, придатний для наступного POST.

**Результати:** Помилки валідації, cooldown, помилка публікації в broker та успіх
зазвичай повертають 200, а не 429 чи redirect. Очікувані відмови Redis стають
`RateLimitUnavailable`; спільний mixin зупиняє обробку й повертає bound partial
із локалізованою помилкою, CSRF-токеном і HTTP 503, також без глобальних context
processors. Необроблені помилки програмування/provider не перетворюються на
успіх. Після успішного надсилання view не скидає limiter.

**Фонове продовження:** Celery task використовує `translation.override(language)`
і викликає `main.services.email.send_contact_email`. Сервіс запитує назву активної
компанії, готує `main/contact_email.html` і викликає спільний HTML email service
для `COMPANY_CONTACT_EMAIL`. Доставку виконує налаштований email backend.
Винятки передаються Celery; task ігнорує результати та не налаштовує автоматичний
retry. Помилка доставки не змінює вже повернену HTTP-відповідь. Контактне
звернення не зберігається в БД.

## ProjectListView

**Призначення / запит:** Каталог GET `/projects/` (`main:project_list`).

1. Прочитати `category`. Приймати `residential` або `commercial` із
   `ProjectCategory.values`; відсутнє чи непідтримуване значення дає `all`.
2. Побудувати queryset Project, за потреби відфільтрувати категорію та зберегти
   модельне сортування за спаданням ID. Кеш головної сторінки тут не використовується.
3. Застосувати Django pagination по шість проєктів через параметр `page`.
4. Додати `current_category` до стандартного контексту списку/pagination,
   передати об'єкти сторінки як `projects` і відрендерити `main/project_list.html`.

**Результати:** Зазвичай 200, включно з порожньою першою сторінкою. Некоректна
чи позамежна сторінка дає 404; підтримується стандартне Django `page=last`.
Непідтримувана категорія показує всі проєкти замість помилки.

## ProjectDetailView

**Призначення / запит:** Деталі GET `/projects/<int:pk>/`
(`main:project_detail`).

1. Знайти Project за primary key через ORM.
2. Завчасно завантажити колекцію `images` через prefetch, уникаючи окремих
   запитів для кожного зображення галереї.
3. Передати об'єкт як `project` і відрендерити `main/project_detail.html`
   зі спільним контекстом. Для цього пошуку кеш-сервіс головної не використовується.

**Результати:** 200 для наявного проєкту, навіть без фотографій галереї;
404, якщо проєкту немає. URL converter відхиляє нецілі значення в цьому сегменті.

## Privacy Policy TemplateView

**Призначення / запит:** Сторінка GET `/privacy_policy/` (`main:privacy_policy`).

1. URL-конфігурація передає `main/privacy_policy.html` і
   `privacy_policy_updated_on=date(2026, 11, 7)` через `extra_context`.
2. Відрендерити документ зі спільним контекстом. Шаблон використовує один
   фіксований об'єкт дати для обох мов, локалізує його через `DATE_FORMAT`
   і додає ISO-дату до семантичного елемента `time`.

**Результати:** Зазвичай 200. Немає пошуку моделі документа, обчислення дати
з поточного дня, надсилання форми чи фонової задачі. Спільні context processors
усе ще можуть звертатися до кешу компанії та профілю авторизованого користувача.
